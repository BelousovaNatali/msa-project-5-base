### **Название задачи:**
Выбор решения для пакетной обработки данных клиентов

### **Проблема**

Маркетинговый отдел планирует расширенно обрабатывать данные клиентов, объединяя их из разных источников и формируя отчёты. В работе используются данные из:
- Файлового хранилища CSV-файлов со статусами доставок
- PostgreSQL с информацией о заказах
- Данных о платежах по заказам
- Расширенных данных о пользователях
- Kafka с цепочкой событий по модификации заказов

Необходимо выбрать технологическое решение, которое:
- Поддерживает гибкое формирование пайплайнов с ветвлением и условиями
- Интегрируется с BigQuery, Redshift, Kafka и Spark
- Имеет встроенный мониторинг и оповещения
- Легко развёртывается в облачной инфраструктуре

### Решение

Для реализации пакетной обработки данных выбран **Apache Airflow** как оркестратор пайплайнов.

### Логика принятия решения

Выбор Apache Airflow основан на сравнении с основными альтернативами:

| Критерий              | Apache Airflow   |
|-----------------------|------------------|
| Ветвление и условия   | ✅                |
| Интеграция с BigQuery | ✅ из коробки     |
| Интеграция с Redshift | ✅ из коробки     |
| Интеграция с Kafka    | ✅ из коробки     |
| Интеграция со Spark   | ✅ из коробки     |
| Встроенный мониторинг | ✅ UI + логи      |
| Retry-политика        | ✅                |
| Оповещения            | ✅ Email/Slack    |
| Fallback-логика       | ✅ trigger_rules  |

#### Описание работы пайплайна

1. **Запуск** — пайплайн запускается ежедневно в 2:00 по расписанию или вручную через UI

2. **Чтение данных**:
   - PostgreSQL — заказы за последний день
   - CSV-файлы — статусы доставок
   - Kafka — события изменений заказов

3. **Обработка** — данные денормализуются, объединяются, агрегируются, формируются отчёты

4. **Запись результатов** — отчёты сохраняются в BigQuery, при ошибке — fallback в локальный CSV

5. **Мониторинг и оповещения** — при ошибке — Email с указанием проблемы и ссылкой на логи

6. **Retry** — при временных сбоях задача перезапускается до 3 раз с экспоненциальной задержкой

---

#### Надёжность и мониторинг

**Устойчивость (Resiliency):**
- Все DAGи описаны декларативно — можно перезапустить с любой точки
- Состояние хранится в Metadata DB — после перезапуска известно, что уже выполнено
- Задачи изолированы — падение одного шага не ломает весь пайплайн
- Возможность перезапуска упавших задач через UI

**Повторные попытки (Retry):**
Для каждой задачи настраивается:
- Количество попыток
- Задержка между попытками
- Экспоненциальный backoff

**Оповещения:**
- Email-уведомления при успехе или ошибке
- Интеграция с Prometheus/Grafana для метрик

### Итоговое решение

Выбран **Apache Airflow** как наиболее подходящее решение, поскольку он:

- Закрывает 100% функциональных требований
- Имеет готовые интеграции со всеми необходимыми системами
- Обеспечивает надёжность через встроенные механизмы retry, fallback, SLA
- Позволяет гибко настраивать пайплайны с ветвлением и условиями
- Не привязывает к конкретному облачному провайдеру
