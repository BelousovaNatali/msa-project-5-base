# Выбор решения для пакетной генерации B2B-прайс-листов

### Сравнительный анализ

| Критерий                                                                    | Spring Batch                                                                           | Apache Airflow                                                                                   | K8s CronJob                                                                       | Apache Spark                                                                  |
|-----------------------------------------------------------------------------|----------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------|-------------------------------------------------------------------------------|
| Наличие конфигурации CRON-расписания                                        | Есть, но требует дополнительной настройки Quartz                                       | Есть из коробки, достаточно указать CRON-строку                                                  | Есть из коробки, встроено в Kubernetes                                            | Нет, нужно ставить отдельный оркестратор                                      |
| Сложность реализации логики по обработке данных                             | Средняя — нужно писать много Java-конфигураций (ItemReader, ItemProcessor, ItemWriter) | Низкая — пишется простой Python-скрипт с SQL-запросом                                            | Низкая — пишется простой скрипт на Node.js/Python                                 | Высокая — для 10k записей это как из пушки по воробьям, нужно знать Spark API |
| Ресурсоёмкость решения                                                      | Низкая — одно JVM-приложение, памяти нужно 256–512 МБ                                  | Средняя — нужен веб-сервер, база для метаданных, воркеры                                         | Низкая — под запускается, отработал и завершился                                  | Очень высокая — нужен целый кластер, гигабайты памяти                         |
| Масштабируемость под нагрузкой                                              | Средняя — можно запустить несколько инстансов, но сложно настроить                     | Высокая — можно добавить воркеров                                                                | Высокая — можно настроить параллельные Job в Kubernetes                           | Очень высокая — создан для больших данных, но для 10k не нужно                |
| Сложность развёртывания в облаке и интеграция с микросервисной архитектурой | Средняя — нужно писать Dockerfile, настраивать Java-приложение, интегрировать в CI/CD  | Высокая — нужно разворачивать отдельный сервис с веб-интерфейсом, базой, настраивать подключения | Низкая — в облаке уже есть Kubernetes, просто применяется CronJob-манифест        | Высокая — нужно разворачивать Spark-кластер, настраивать менеджер ресурсов    |
| Удобство интеграции с логированием и мониторингом                           | Средняя — логи через SLF4J, метрики через Actuator, нужно дополнительно настраивать    | Высокая — есть встроенный UI, логи и интеграции с Prometheus/Grafana                             | Средняя — логи через kubectl logs, метрики собираются через Prometheus стандартно | Средняя — логи и метрики есть, но сложно настраивать                          |

### K8s CronJob лучше всего подходит для этой задачи:

**1. Простота реализации**
Для выполнения задачи достаточно написать один скрипт на Node.js (например), который подключается к базе данных, выполняет SQL-запрос с JOIN'ами и сохраняет результат в CSV. Скрипт оборачивается в Docker-образ, и всё готово к запуску. Никаких сложных конфигураций и фреймворков не требуется.

**2. Низкая ресурсоёмкость**
Pod с приложением запускается только в 6:00 утра, выполняет работу в течение нескольких минут и завершается. Всё остальное время ресурсы кластера не потребляются.

**3. Использование существующей инфраструктуры**
Магазин уже работает на микросервисах в облаке, а значит Kubernetes уже развёрнут в кластере.

**4. CRON-расписание из коробки**
Kubernetes имеет встроенный ресурс CronJob, который нативно поддерживает запуск по расписанию. Достаточно указать строку `"0 6 * * *"` в манифесте, и задача будет запускаться каждый день в 6 утра без дополнительных настроек.

**5. Масштабируемость при росте нагрузки**
Если в будущем объём данных увеличится или появится необходимость генерировать прайс-листы для большего числа клиентов, Kubernetes позволяет настроить параллельное выполнение Job.

**6. Встроенные механизмы надёжности**
Kubernetes предоставляет встроенные инструменты для обеспечения надёжности: политика перезапусков, ограничение количества попыток, таймауты. Всё это настраивается в манифесте.

**7. Удобство мониторинга**
Логи выполнения доступны через команду `kubectl logs`. Метрики собираются через Prometheus и оповещения можно настроить.

### Почему альтернативы не подходят

| Решение        | Почему не подходит                                                                                                                                                                                          |
|----------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Spring Batch   | Требует написания большого количества Java-конфигураций (ItemReader, ItemProcessor, ItemWriter). Слишком сложный фреймворк для простого SQL-запроса на 10 тысяч записей. Оверхед по разработке и поддержке. |
| Apache Airflow | Требует развёртывания отдельного сервиса с веб-интерфейсом, базой данных и воркерами. Для одной простой задачи это избыточно.                                                                               |
| Apache Spark   | Создан для обработки терабайтов данных в распределённом кластере. Использовать Spark для 10-20 тысяч записей — это огромный оверхед.                                                                        |

---

### Вывод

Kubernetes CronJob является оптимальным решением для этой задачи.
